# Data model

## Current PostgreSQL schema

EF Core migrations live in `src/OpenBudget.Api/Migrations`.

### Identity and account lifecycle

ASP.NET Core Identity stores users, password hashes, roles, lockout state, email confirmation and security stamps in its `AspNet*` tables. `AspNetUsers` adds suspension, bootstrap-administrator, pending-approval, creation-time and last-login fields. `ApplicationSettings` stores the administrator-selected registration mode; the default is Disabled. `SmtpSettings` stores the one administrator-managed SMTP connection: host, port, sender address, optional username, TLS choice, update time, and an ASP.NET Data Protection-encrypted password. Passwords are never returned from the API or written to audit records. `AdminAuditLogs` records the actor, target, action and timestamp for registration, registration-policy, email-settings and account-lifecycle actions. Verification and reset tokens use Identity's data-protection token providers and are sent through configured SMTP; tokens are not persisted in application tables.

### Agent tokens and MCP audit

`AgentTokens` stores personal access tokens for the owner's AI agents: ID, owning user (cascade on user deletion), name (80), display prefix (`obk_` + 8 characters), the lowercase hex SHA-256 `TokenHash` (64, unique index; the plaintext is never stored), permission (`Admin`, `Budget`, `Reporting` stored as text), created/expires/last-used/revoked timestamps. `AgentTokenBudgets` is the Budget/Reporting allow-list (token ID + budget ID, both cascading); Admin tokens have no rows and use every budget the creator can access at call time. `AgentAuditLogs` keeps one row per MCP tool call: token ID, user ID, tool name, optional budget ID, success flag, outcome code (`ok`, `invalid`, `confirm_required`, `denied`, `not_found`, `conflict`, `error`), status code and time. It intentionally has no column for arguments, results, amounts or tokens; ledger command receipts remain the financial audit. Indexes support per-token and per-user recent-activity reads. Migration: `AgentTokensAndAudit`.

### `BudgetPlans`

`BudgetPlans` stores a globally unique ID, display name, currency, nullable owner during the legacy-data transition, archive state, creation timestamp and concurrency version. Startup assigns the existing `default` plan to the configured bootstrap administrator. `BudgetMembers` grants editor access with the inviting user and join time; `BudgetInvitations` retains a unique normalized email per budget until that verified address signs in. Owners retain lifecycle and sharing administration. `PlanActions` is the immutable, budget-scoped Recent Moves feed with month, actor, action kind, amount, source/destination category and timestamp. Budget deletion cascades collaboration/history rows. `MembershipPlans` seeds Free (1 active budget), Plus (3) and Pro (unlimited); shared budgets do not consume the editor's owned-budget quota. `UserMemberships` assigns a tier and optional per-user active-budget override plus optional start/expiration dates and billing-provider/external-subscription metadata. `MembershipPlanEntitlements` stores per-tier feature defaults, while `UserEntitlementOverrides` provides explicit per-user allow/deny decisions. `EntitlementService` resolves user override first, then the assigned tier, and `RequireEntitlement` applies that result as an authorization requirement. Registration assigns Free; the bootstrap administrator receives Pro. Budget creation/restoration serializes quota checks per owner. Subscription fields are metadata only; no billing provider or entitlement is activated by them.

Monthly Plan snapshots, groups and categories use composite budget/month keys and foreign keys. The legacy snapshot rows remain attached to `default`; each new budget initializes and carries its own month/category history. Access-checked Plan routes filter by the budget ID for owners and joined editors. Ledger and long-term planning rows carry `BudgetId`; EF query filters and the selected-budget request context partition account, transaction, payee, schedule, reconciliation, command, view, flag, and planning data. Existing financial rows are backfilled to `default` without changing their IDs, balances, names, or revision values.

### Long-Term Planning

`LongTermPlanningStates` holds one budget-specific planning version for optimistic concurrency. `LongTermPlanningIncomes` and `LongTermPlanningCategories` use `(BudgetId, Month[, CategoryId])` keys. Expected income and expenses are projected from active scheduled ledger transactions in that budget; their old stored planning fields are no longer used for forecasts or accepted by the planning update API. `LongTermPlanningCategories` stores effective-month `PlannedBudgetOverride` values. A null override means inherit the most recent earlier override; an explicit zero is a real override. The planning tables do not update monthly budget snapshots.

The annual forecast calculates `Planned Budget` from the latest effective override and `Planned Available = prior planned available + planned budget - scheduled category expenses`, starting from zero before the first planning event. Calculations include earlier months when a year is loaded, so a December plan carries into January. Expected expenses sum all scheduled outflows except transfers, including uncategorized outflows; `Remaining = expected income - expected expenses` and `Remaining to Be Assigned = expected income - the sum of planned category budgets`. Past-month mutation is rejected using server-local time.

Actual assigned and activity come from stored category snapshots. Actual expenses display as the negated signed activity (refunds reduce net expenses), and actual available comes from the snapshot's server-calculated available value. Missing actual months do not create snapshots; their actual available display carries forward from the nearest earlier stored snapshot while assigned and expense remain unavailable. The category structure is read from the latest existing monthly snapshot.

### `Budgets`

One row per budget and `YYYY-MM` snapshot, with primary key `(BudgetId, Month)`, linked to a budget plan. `OpeningReadyToAssign`, preserved legacy `FundsAdded`, and materialized `LedgerIncome` are inputs to Ready to Assign; `Version` guards concurrent edits; `Note` stores the month note.

### `CategoryGroups` and `Categories`

Groups and categories are keyed by `(BudgetId, BudgetMonth, Id)` and their foreign keys include the budget ID. Groups are ordered and can be archived. Categories have a month-scoped stable ID and a mutable group membership/order, so moving one between active groups preserves its identity and ledger links. Ordering is a shared budget-level presentation setting: a successful group/category reorder synchronizes the matching initialized rows in every month, while month-specific financial values and metadata remain local to each snapshot. Categories store assignment, target, icon, snooze, archive state, `OpeningAvailable`, and `LegacyActivity`. Materialized `Activity` is legacy activity plus nondeleted, non-transfer single-category/split ledger amounts in that month. `Available = OpeningAvailable + Assigned + Activity`; calculated fields are not accepted from browser writes.

### Register view preferences

`RegisterViews` stores one row per `(BudgetId, Scope)` using a canonical account UUID or independent `all` scope. It contains its own optimistic version, date preset, nullable From/To month selectors, five visibility switches, and column widths. The application validates account existence and every selection before writing under the budget-specific PostgreSQL gate. Reads of unsaved scopes return defaults without inserting. Account deletion is not supported; closed-account preferences remain available. Preferences are server-owned and shared across clients of the same budget.

### Ledger tables

- `Accounts`: UUID, `BudgetId`, name, closed flag, account type (`checking`/`savings`/`cash`, or credit `creditCard`/`lineOfCredit`) favorite flag and notes (AccountNotes migration, empty default). Balance is derived from nondeleted transactions in the same budget; cleared balance includes cleared/reconciled entries, uncleared balance is the remainder. `AccountRegisterPresentation` adds type/favorite with checking/false defaults, preserving existing balances.
- `Transactions`: UUID, `BudgetId`, account/payee FKs, date, signed decimal amount, memo, optional logical category ID, cleared status, optional shared transfer ID, opening and soft-delete flags. Indexes support date/account/UUID pagination and transfer lookup. Account/payee deletion is restricted.
- `SplitEntity`: transaction FK plus position key, category ID and signed amount, with optional per-part payee and memo. Parts must sum exactly to the parent amount. The service validates categories against the transaction month's retained category records.
- `Payees`: UUID, `BudgetId`, display/normalized name; normalized names have a budget-scoped unique index and are reused case-insensitively.
- `LedgerStates`: one row per budget (ID 1) with that budget's revision. A budget-keyed PostgreSQL advisory lock plus `SELECT ... FOR UPDATE` orders commands, Plan writes and month initialization across API processes.
- `LedgerCommands`: command ID primary key and `BudgetId`, resource ID, kind/path, SHA-256 input fingerprint, before/after JSON, revision and UTC timestamp. Append-only receipts provide replay safety and audit atomically with ledger/projection changes.
- `Reconciliations`: UUID, account FK, confirmed statement balance and UTC time. Confirmation marks cleared entries reconciled. `IsInvalidated` retains the snapshot after an explicitly confirmed reconciled edit; the entry becomes cleared and audit records the change. Deletion remains blocked while reconciled.

## Calculations and month lifecycle

- `Ready to Assign = OpeningReadyToAssign + FundsAdded + LedgerIncome - sum(Assigned)` for the month. Ledger income sums nondeleted/non-transfer entries without categories/splits, including opening balances and negative uncategorized spending. Categorized positive amounts are refunds; transfers are budget-neutral.
- Category available values and totals are calculated with .NET decimal arithmetic and rounded to two places.
- The first requested month gets a deterministic blank starter structure. A later unseen month carries each positive prior category amount into `OpeningAvailable` and resets assignment/activity. A negative prior category amount opens at zero and is added as a negative adjustment to `OpeningReadyToAssign`, alongside the prior Ready to Assign.
- Month initialization is persisted once. Repeated and concurrent GET requests return the same month record.
- The BudgetCore migration converts prior persisted `Available` into `OpeningAvailable = Available - Assigned - Activity`, preserving existing visible category balances. It seeds `FundsAdded` with prior total assignments to preserve the former zero Ready to Assign display.
- The CashLedger migration copies existing `Activity` to `LegacyActivity`, adds zero `LedgerIncome` and empty ledger tables, and preserves all existing assignments/opening balances/manual funds. It fabricates no account/transaction history. Manual funds become read-only; record new income through accounts.
- On each ledger write, initialized months are recalculated chronologically. Positive category carry and uncovered-overspending Ready to Assign adjustments propagate as deltas into later opening values, preserving later explicit assignments and legacy baselines. Affected month versions increase. Date/category/account edits reverse their original effects and apply new ones atomically. Repeated recomputation does not duplicate carry-forward.
- Positive available balances carry into the same category. Negative available balances do not carry into that category; the next month opens it at zero and subtracts the uncovered amount from Ready to Assign. Assignment saves and ledger changes both propagate exact corrections through every initialized later month. Later explicit assignments, activity, metadata and preserved legacy opening baselines remain intact. Affected month versions advance; unchanged money/metadata-only saves do not invalidate later months.
- Existing prototype funds/activity and new account opening entries are additive. Do not count previously entered funds a second time when selecting an opening balance; there is no automatic conversion of untraceable demo activity into real transactions.
- Register running balances are PostgreSQL window sums partitioned by account over all nondeleted history, ordered date ascending/UUID descending, then filtered to page IDs. They are not recomputed from the visible rows. Display order reverses that window. The latest account reconciliation date and attention count are derived, not browser-entered. Connection status is unlinked until a real sync provider exists.

## Limitations and direction

Budget identity, monthly Plan snapshots, ledger resources and long-term planning are scoped to the selected owned budget. The UI stores the selection locally and sends it in a non-secret cookie; the API verifies ownership and active status before applying it. The legacy default routes remain administrator-only. Credit-card payment categories and category targets are implemented (see below); loan accounts, payoff planning, bank connections, imports, target pause/snooze semantics, templates and recommendation previews remain outside this slice. Account balances are ledger queries; monthly projections read initialized months from the active budget and its ledger. Persist money as fixed-precision decimals, never binary floating point.

### Scheduling and flag storage

`ScheduledTransactions` migration adds `Schedules`, `ScheduleOccurrences`, a nullable transaction `ScheduleId` and reconciliation invalidation state without changing existing amounts or statuses. Rules store source/destination account FKs, original calendar anchor, next date, recurrence index, monotonic sequence, validated template JSON, pause/end state and optional end bounds. Occurrences have deterministic UUIDs derived from rule UUID/sequence, a unique rule/sequence index, original due date, optional snooze/override, disposition and generated transaction link. Rule edits increment sequence without reusing occurrence identities. Historical posted/skipped/superseded records are retained. All commands share the ledger transaction/receipt/audit path.

`TransactionFlags` adds nullable flag colors to transactions/rules and seeds six `FlagDefinitions` keyed by fixed color. Names are mutable per budget; colors remain fixed. Flags change no financial values or reconciliation state. The account balance-adjustment workflow appends ordinary cleared transactions; it adds no mutable balance column. API/domain validation owns template and flag integrity; JSON persistence is internal, never accepted as unchecked JSON from a client.

`ScheduledApproval` adds transaction `IsApproved` with a true backfill/default, preserving existing manual/history rows as approved, plus nullable schedule `PostingError`. Due processing generates deterministic uncleared/unapproved transactions and advances occurrences under the same lock/receipt/projection transaction. Approval is separate from cleared state: clearing implies approval, while pending actual amounts already participate in financial totals. Rejection soft-deletes and reverses the posted entry/pair; occurrence history prevents regenerated duplicates. Account attention counts are derived from nondeleted entries. Scheduler polling/catch-up uses the server clock/local date through TimeProvider, not browser clocks.


## Payee management

The `PayeeManagement` migration adds `IsHidden` (false), `CategoryMode` (history), nullable `DefaultCategoryId`, and `RulesJson` (empty array) to existing stable `Payees` rows. Normalized names are unique within a budget. Rules use public `PayeeRuleDto` contracts serialized by the application service, separate from persistence entities. Existing names/history/money are preserved. Transfer payees are derived from Accounts rather than duplicate merchant records.

Settings mutations and accepted imported rows use the shared ledger gate/receipt and global version. Payee rename changes labels through the existing foreign key and updates active schedule/pending override names atomically. Imported source names are retained in the command audit; normal money projections include unapproved imported rows. Default category IDs are logical budget category IDs across months; application checks category/group activity in the transaction month. There is no new financial total stored on a payee. See [API](api.md#saved-payees-and-renaming-rules) for matching priority, history tie rules, deletion protection and the accepted-row import boundary.


### Backdated assignment corrections

`BudgetCarryForward` applies the same decimal opening-balance rules for monthly assignment saves and ledger recomputation. Available remains opening available + this month's assigned + this month's activity. Assignment edits change only the selected month's assigned value; the resulting positive available carry and uncovered-overspending Ready to Assign adjustment recalculate later months in the same database transaction. No later assignment is copied or replaced. Missing calendar months do not consume/reset carry; when opened they initialize from the nearest earlier month as usual.

If a historical category did not exist in an already initialized later month, a zero-assigned/zero-activity category record (and group if needed) is created there to retain the incoming amount. Existing later category/group names and archive state are preserved; newly needed rows append with distinct ordering. Explicit reorders are different: matching initialized rows in all months receive the same group/category order (and group membership when a category is moved), while rows that do not exist in a snapshot remain absent. Ledger recomputation uses the same helper so refunds, recategorization, amount/date edits and soft deletion cannot drop that carry across missing category rows. All calculations use decimal; reads do not reapply saved changes.

This preserves explicit opening/legacy baselines rather than replacing historical snapshots wholesale. The gate rolls back invalid or stale monthly updates, including any month initialized during that rejected request. A save failure after the database writes rolls back source and future rows together. There is no schema migration or automatic replacement of old baseline values in this fix.

### Credit accounts

The `CreditAccounts` migration adds `Categories.CreditOverspending` (numeric(14,2), default 0). No existing rows change: existing accounts remain cash types and the column is zero until a credit account exists.

`LedgerProjection` is the shared month recalculation for ledger commands and, when a budget has credit accounts, monthly Plan saves. For every initialized month it ensures the `credit-card-payments` group (first in order) and one `ccp-{accountId}` category per credit account, named after the account. Card spending moves the portion covered by the spending category's funds (opening + assigned + legacy + cash activity, after same-month card refunds) into that card's payment category; the uncovered portion is stored as `CreditOverspending`. At rollover `BudgetCarryForward` subtracts only `min(Available + CreditOverspending, 0)` from Ready to Assign, so credit overspending becomes card debt instead of reducing next month's budget. Transfers into a card reduce its payment category. Credit opening balances are excluded from `LedgerIncome`. See [API](api.md#credit-accounts-and-card-payments) for worked examples.

The `CreditPayoffTargets` migration adds one optional debt payoff target per credit account: `AccountId` (primary key, FK to `Accounts`, restrict delete), `BudgetId` (indexed, budget query filter and stamping like other ledger rows), `Kind` (`payByDate`/`monthlyAmount`, max 20), nullable `TargetMonth` (`YYYY-MM`), nullable `MonthlyAmount` numeric(14,2), `PayoffAmount` numeric(14,2) (card debt when last saved) and `CreatedAt`/`UpdatedAt`. Writes go through ledger commands (version, replay receipt, audit). Progress is not stored; it is recalculated per Plan month from the card ledger and the payment category's Available/Assigned (see [API](api.md#debt-payoff-targets)). The existing `Categories.Target` column is not used for payment categories, so the Underfunded filter and auto-assign are unchanged.

### Loan accounts

The `LoanAccounts` migration adds `LoanTerms`, one row per loan/contract account: `AccountId` (primary key, FK to `Accounts`, restrict delete), `BudgetId` (budget query filter and stamping like other ledger rows), `InterestRate` numeric(6,3), `MinimumPayment`, `EscrowAmount`, `OriginalBalance` numeric(14,2), nullable `PairedCategoryId` (max 100; unique per budget when set), nullable `BalanceConfirmedAt`, and contract columns (`ContractMonths`, `ContractStartDate`, `IncludesDevice`, `UpfrontCost`, `MonthlyServiceCost`, `DeviceTotal`, `DiscountMonths`, nullable `DiscountedServiceCost`). Rows are written only by ledger commands (account create/update, `loan.terms/{id}`, `loan.balance/{id}`), so every change has a version, replay receipt and before/after audit. `OriginalBalance` is the opening debt (contracts: remaining commitment at the start date) and is the base for "% remaining". Projections, interest estimates, activity months and contract schedules are calculated on read and never stored.

`LedgerProjection` treats loan accounts as follows for every initialized month: ensures the `loan-payments` group ("Loans", appended after existing groups) and each automatically paired `loan-{accountId}` category; excludes all loan-account entries from income (Ready to Assign); and adds `LoanRules.Project` flows: a non-loan → loan transfer is paired-category activity (or negative income when unpaired), a loan → non-loan transfer the reverse, loan ↔ loan neutral. Plan saves recalculate when a budget has credit **or** loan accounts. Account type is `varchar(20)`, so the new type names need no schema change.

### Category targets

The `CategoryTargets` migration adds one optional structured target per budget and logical category ID: primary key `(BudgetId, CategoryId)` (`BudgetId` FK to `BudgetPlans`, cascade delete; `CategoryId` max 100, the stable ID shared by every month snapshot), a unique resource `Id` (UUID used by command receipts), `Kind` (`weekly`/`monthly`/`yearly`/`custom`), `Amount` numeric(14,2), `Behavior` (`setAside`/`refill`), nullable `Weekday` (0-6), `DayOfMonth` (1-31, null = last day), `DueDate` (date), `RepeatEvery` (1-99) and `RepeatUnit` (`day`/`week`/`month`/`year`), `StartMonth` (`YYYY-MM`, start of the current funding cycle), `Version` (optimistic concurrency token) and `CreatedAt`/`UpdatedAt`. Rows are partitioned by the budget query filter and stamped with the request budget like ledger rows. No existing data changes; the legacy `Categories.Target` decimal stays in place and is still round-tripped by Plan saves, but structured targets are separate and payment categories (`credit-card-payments` group, `ccp-*` IDs) are rejected.

Progress is never stored. `BudgetService` recalculates it for each month DTO from the target, that month's `Assigned`/`Available`, and (for "set aside" yearly/custom targets) earlier months' `Assigned` from `StartMonth` onward, using `CategoryTargetRules` with decimal arithmetic and round-up-to-cent spreading. Writes run under `LedgerGate`, validate the category in the requested month, check `Version`, and append a `LedgerCommands` receipt (`categoryTarget.save/{categoryId}` / `categoryTarget.delete/{categoryId}`) with before/after JSON in the same transaction without advancing the ledger revision. See [API](api.md#category-targets) for formulas and worked examples.

### Wishlist

The `Wishlist` migration adds three budget-scoped tables and seeds `MembershipPlanEntitlements` rows for key `wishlist` (Free disabled, Plus/Pro enabled). No existing rows change.

- `WishlistSettings`: primary key `BudgetId` (FK to `BudgetPlans`, cascade delete), `IsEnabled`, `Version` (optimistic concurrency token guarding every Wishlist write for the budget) and `UpdatedAt`.
- `WishlistBuckets`: UUID `Id`, `BudgetId` (FK to `BudgetPlans`, cascade), `Name` (max 60), `SortOrder` (contiguous among active buckets), `IsDeleted` (soft delete/archive) and `CreatedAt`/`UpdatedAt`; indexed by `(BudgetId, IsDeleted, SortOrder)`.
- `WishlistItems`: UUID `Id`, `BudgetId`, `BucketId` (FK to `WishlistBuckets`, cascade), `Name` (max 120), nullable `Url` (max 2048), `Cost` numeric(14,2), `Description` (max 1000), `SortOrder` (desire order among the bucket's active items), `Status` (`active`/`purchased`/`removed`), `CreatedAt`, `UpdatedAt` and nullable `PurchasedAt`/`RemovedAt`; indexed by `(BucketId, Status, SortOrder)` and `BudgetId`.

Wishlist rows are filtered explicitly by budget ID in `WishlistService` (no global query filter). Money lives only in the Plan snapshot: each bucket owns category `wl-{bucketId}` in group `wishlist` of every initialized month, kept in sync by `WishlistRules.EnsureCategories` on Wishlist writes (and on Wishlist reads of a month created before the earliest initialized month). Deleted buckets keep an archived category; disabling archives the group. Progress is never stored; it is recalculated from the category's `Available` and the top active item. Assignment, carry-forward and Ready to Assign are unchanged for Wishlist categories.

### Transaction images

The `TransactionImages` migration adds two tables. `TransactionImages` holds metadata only: UUID primary key, `BudgetId`, `TransactionId` (FK to `Transactions`, cascade), sanitized `FileName` (100), detected `ContentType` (20), `SizeBytes`, `Width`/`Height` from the image header, SHA-256 of the stored bytes, `Source` (`upload`/`url`), optional `CreatedByUserId` and `CreatedAt`; index `(BudgetId, TransactionId, CreatedAt)`. `TransactionImageBlobs` holds the validated, metadata-stripped bytes (`bytea`) keyed by `ImageId` (FK to `TransactionImages`, cascade) with its own `BudgetId`, so register counts and listings never read image content. Both tables have the active-budget query filter and are stamped with the active budget on insert.

Images are not financial data: they never change balances, Activity or the ledger revision. Image rows of soft-deleted transactions are retained but hidden. Explicit image deletion is a hard delete of both rows; the audit receipt in `LedgerCommands` (metadata only) remains.
